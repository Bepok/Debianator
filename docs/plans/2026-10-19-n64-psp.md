# N64 and PSP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Nintendo 64 (mupen64plus-next) and PSP (PPSSPP) as experimental systems in ES, cores cross-compiled in the
build container, measured on the device with Super Smash Bros., Mario Kart 64 and Castlevania DXC.

**Architecture:** A new cross-build step (`scripts/build-cross.sh`, run as the user in the build container) builds
both cores with `arm-linux-gnueabihf-g++` against armhf headers from Debian multiarch, into `out/cross`. The existing
apps chroot copies them into its stage before it derives the run-time packages with `ldd`, so the rootfs stage needs no
change. ES entries, core option files and the PPSSPP assets ride the existing overlay and `ga36-roms-dirs`.

**Tech Stack:** Debian trixie armhf, GNU make / CMake cross builds, libretro (RetroArch 1.20, GLES2 on lima),
POSIX sh tests run with `./build.sh run`.

**Spec:** [`../specs/2026-10-19-n64-psp-design.md`](../specs/2026-10-19-n64-psp-design.md)

## Global Constraints

- Both cores are GLES2 builds (Debian's armhf RetroArch is GLES2; lima has nothing newer). Neither may link `libGL.so`.
- CPU flags: Cortex-A7, NEON, hard-float, ARM (not Thumb) mode. `readelf -A` must say `Tag_CPU_arch: v7`.
- mupen64plus-next: `libretro/mupen64plus-libretro-nx`, branch `develop`, pinned by commit; `platform=unix-armv7-neon-hardfloat FORCE_GLES=1`; never `CPUFLAGS=` on the command line; the ARM dynarec must be in.
- PPSSPP: tag `v1.20.4` with submodules; `-DLIBRETRO=ON -DUSING_GLES2=ON -DVULKAN=OFF`.
- The cores are cross-compiled, not built under qemu; under qemu is the fallback only if a core resists, and CI must stay under 6 h.
- PSP: frame skip 0, auto frame skip off. Emulated CPU clock at the PSP default.
- Audio resampler: RetroArch's default (`sinc`), unchanged.
- N64: 320x240, framebuffer emulation off, controls are the core's defaults (no remap files).
- Saves on `/roms/saves`; RetroArch's system directory is `/roms/bios`, so PPSSPP's assets live in `/roms/bios/PPSSPP`.
- ES names: `n64` "Nintendo 64" `/roms/n64` `.n64 .z64 .v64 .zip`; `psp` "PSP" `/roms/psp` `.iso .cso .pbp .chd`; each extension in both cases; themes `n64` and `psp` (the carbon theme has both).
- Existing systems' launch, cores and settings unchanged. No game data in the repo or the image.
- On the device: if a core runs but does not render or crashes on lima, N64 tries parallel-n64 (GLES2 plugins) before it is given up; PSP is dropped from v1.1. If a game does not fit in memory with ES behind it, the N64 and PSP launches may stop ES for the game's run.

## Review Focus

- A core built without its JIT/dynarec (plain `platform=unix` under some `uname -m`, a wrong CMake CPU guess) still loads and runs, only far too slowly: Task 2 and Task 3 assert the dynarec / JIT is compiled in, and Step 2 of each proves the check fails on a build without it.
- A cross-built core that links an armhf library the rootfs does not install starts in the build but fails with "cannot open shared object" on the device: Task 4 asserts every `NEEDED` of both cores resolves in the rootfs tarball.
- The PPSSPP assets missing or stale on `/roms` (a fresh card, or a card from an older image) give missing fonts or a failed start: Task 4's `roms-part.sh` checks the copy when missing and the refresh when the shipped version differs.
- A ROM copied from Windows with an upper-case extension (`GAME.Z64`, `GAME.CSO`) must show in ES: Task 4 checks both cases of every extension.
- A game that fails to start (crash, black screen) must return to ES, not leave the console stuck: Task 5 Step 4 starts a broken file on purpose.
