# N64 and PSP design

Date: 2026-10-19. Status: design. Release: v1.1 ("N64 and PSP" in [`../porting-plan.md`](../porting-plan.md)).
Parent design: [`2026-10-14-firmware-design.md`](2026-10-14-firmware-design.md).

**Changed on 2026-10-20 (owner):** N64 ships **parallel-n64** (libretro, `platform=classic_armv7_a7`, gln64 renderer
at accuracy "low", dynarec, 320x240) instead of mupen64plus-next. GLideN64 was GPU-bound on lima and drew broken
menus; gln64 doubles Mario Kart's speed with a clean picture. The mupen64plus-next sections below are the original
design, kept for the record. Measurements: [`../research/2026-10-20-n64-performance.md`](../research/2026-10-20-n64-performance.md).

## Why

The owner wants Nintendo 64 and PSP games on the GA36. The hardware (4x Cortex-A7 at 1.2 GHz, 512 MiB, Mali-400 MP2
on mainline lima, GLES2 only) is at the bottom of what these systems need: DOSBox Pure runs Doom at 19 fps here,
CPU-bound. Both systems therefore ship as **experimental, however they measure**: the roadmap decided that, and the
measured speed is published rather than promised.

A twin device shows it can be done: the Miyoo A30 is the same A33 with 512 MB, and its custom firmware (spruceOS)
ships N64 and PSP today, on a vendor 3.x kernel with the Mali blob instead of lima. No frame rate for these games on
an A33 has been found published anywhere, so ours are the first numbers.

## Behaviour (decided with the owner)

- Two new systems in EmulationStation, **Nintendo 64** and **PSP**, launched like the others, marked experimental in
  the README with the measured speed of each benchmark game.
- Benchmark games, from the owner's own collection:
  - N64: **Super Smash Bros.** (the lighter one) and **Mario Kart 64** (the heavier one);
  - PSP: **Castlevania: The Dracula X Chronicles** (`.cso`). Our pick: continuous music makes audio problems easy to
    hear, 2.5D play tolerates a low frame rate, and its load sits between the small PSN titles and Tekken or GTA.
- **PSP: no frame skip.** Told that skipping frames can free CPU time for the
  emulated CPU (which is what keeps PSP music at the right speed), the owner still chose no frame skip, accepting that
  the music slows down when a game is too heavy. (Earlier the owner put sound in sync above smooth video; sound
  quality as such is not a priority.)
- If a game does not fit in memory with ES running behind it, the N64 and PSP launches may stop ES while the game
  runs and start it again when the game exits. Other systems keep today's launch.
- If a core runs but does not work on lima (black screen, crash): **N64** first tries a lighter alternative before it
  is given up (parallel-n64 with its GLES2 plugins glide64, gles2n64 or gles2rice; it has a `classic_armv7_a7`
  platform but is being rewritten upstream, so pin with care); **PSP** has no realistic alternative and is dropped
  from v1.1, the other system ships on its own. The work is split so each system can land without the other.
- Any game can be switched to other settings from the RetroArch menu (FN+X → Core Options) and the change saved for
  that game only (Manage Core Options → Save Game Options). The README says so.
- The cores are **cross-compiled** in the build container, not built under qemu in the armhf chroot.

Our calls, played back to the owner and not objected to:

- Cores: **mupen64plus-next** (libretro, GLideN64 video, ARM32 dynarec) for N64 and **PPSSPP** (libretro) for PSP.
- N64 controls: the core's defaults, which already fit a two-stick pad: left stick = N64 stick, right stick =
  C-buttons, L2 = Z, L1/R1 = L/R, B = A, Y = B (R2 held + face buttons also gives the C-buttons). PSP maps 1:1 with the
  analog nub on the left stick. No remap files.
- N64 renders at 320x240 with the expensive effects off (blurrier, faster); the menu can raise it per game.
- Saves go to the ROMS partition like every other system, so they survive a reflash.

## Goals

- Super Smash Bros., Mario Kart 64 and Castlevania DXC, copied to the ROMS card from a PC as the README says, start
  from ES, take the pad, and return to ES with FN+Start.
- Their speed is measured on the device and written in the hardware notes and the README, whatever it is.
- PSP sound plays without crackling or gaps wherever the emulated CPU keeps up.
- Existing systems, their speed and the tests stay as they are.

## Non-goals

- Full speed for any game. Experimental means "runs and is measured", not "plays well".
- Per-game tuning beyond the defaults (the owner can save per-game options from the menu).
- Standalone mupen64plus or standalone PPSSPP: they do not fit the ES → `ga36-retroarch` launch path.
- CPU overclocking (an open question in the roadmap, "Revisit later").
- Any game data in the image.

## Anti-goals

Even if the cores run, it is a failure if:

- a game can only be started by editing files on the console;
- the CI build no longer fits in a GitHub Actions job (6 h), or the existing cores' build breaks;
- an existing system's launch, speed or controls change;
- a PSP game crackles or drops sound while its emulation keeps up;
- a game that fails to start leaves the console stuck instead of returning to ES.

## How it works

### Build (cross-compiled)

Both cores are pinned in `versions.env` and fetched through `scripts/tree.sh` like the other cores, but built by the
container's armhf cross toolchain instead of in the qemu chroot (the research estimate under qemu: 30-60 min for
mupen64plus-next, 1.5-3 h for PPSSPP; today's CI run is 1 h 24 min).

- The container gains what a C++ armhf cross build needs: `g++-arm-linux-gnueabihf` and armhf development headers
  for GLES2, EGL, zlib and libpng (for example through Debian multiarch, `dpkg --add-architecture armhf`). The
  libraries must match the trixie armhf rootfs the cores run on.
- **mupen64plus-next:** repository `libretro/mupen64plus-libretro-nx`, branch `develop`, pinned by commit.
  `platform=unix-armv7-neon-hardfloat FORCE_GLES=1`, which selects `-marm -mcpu=cortex-a7 -mfpu=neon
  -mfloat-abi=hard`, NEON, GLES2 and `WITH_DYNAREC=arm`. Known traps from the research:
  - a plain `platform=unix` silently builds without the dynarec; the build must prove the dynarec is in;
  - passing `CPUFLAGS=` on the command line replaces `-DARM -marm`;
  - `asm_defines_gas.h` (struct offsets for the dynarec) is generated during the build with `strings` and `awk` from
    an object file, which must work with the cross binutils;
  - upstream moved to 3.0 in September 2026: pin a commit that builds.
- **PPSSPP:** pinned at tag **v1.20.4** (with submodules). Master removed the old ARM32 JIT on 2026-10-14 and
  replaced it with a new one written that week; 1.20.4 still has the proven `ArmJit`. CMake with `-DLIBRETRO=ON
  -DUSING_GLES2=ON -DVULKAN=OFF` and Cortex-A7 NEON hard-float flags; FFmpeg comes prebuilt for `linux/armv7` from
  the `ffmpeg` submodule.
- GLES2 is required: Debian's armhf RetroArch is built for OpenGL ES 2, and lima offers nothing newer.
- Both are GPL-2.0-or-later or compatible, like the other cores.
- The runtime libraries the new cores link (GLES2, EGL, zlib, libpng and anything else) must be in the image; today
  `apps/build-in-chroot.sh` derives that list with `ldd` inside the chroot, and the cross-built cores need the same.

### Runtime

- `es_systems.cfg` gains `n64` ("Nintendo 64", `/roms/n64`) and `psp` ("PSP", `/roms/psp`), through `ga36-retroarch`,
  themes `n64` and `psp` if the carbon theme has them. Extensions, both cases: N64 `.n64 .z64 .v64 .zip`; PSP `.iso
  .cso .pbp .chd`.
- `ga36-roms-dirs` creates the two folders from `es_systems.cfg` as it does today.
- PPSSPP needs its `assets/` folder (fonts, the shader and lang files) in RetroArch's system directory, which here is
  `/roms/bios`, so as `/roms/bios/PPSSPP/`. How it gets there (shipped in the image and copied at boot when missing,
  or pointed at from the root filesystem) is left to the builder; it must survive a reflash and not need the owner.
- Core option defaults ship in `/etc/skel` (no core has shipped option defaults yet; RetroArch writes a per-core
  `config/<core>/<core>.opt`, and the builder picks and proves the mechanism), as starting values (from the A30's settings,
  adapted; the device check may change them):
  - **mupen64plus-next:** dynamic recompiler, GLideN64, HLE RSP, 320x240, framebuffer emulation off, copy colour and
    depth to RDRAM off, legacy blending on, hardware lighting off, no texture filtering. The threaded renderer and the
    VI refresh value are tried on the device (the threaded renderer costs one frame of input lag).
  - **PPSSPP:** JIT, native (1x) resolution, hardware transform, **frame skip 0 and auto frame skip off**, skip GPU
    readbacks on, lower resolution for effects on. Emulated CPU clock left at the PSP's default (an underclock changes
    game timing). `inflight_frames` tried at 1 and 2 (PPSSPP's docs: lower values help music games).
  - RetroArch, for these two cores only (core overrides): audio latency raised (about 96-128 ms) so the buffer does
    not underrun. The resampler stays RetroArch's default (`sinc`): `nearest` saves CPU but distorts whenever the rates
    differ (our call, told to the owner; `nearest` stays an option if CPU time runs short). Whether `video_vsync` off helps N64 is checked on
    the device. `audio_sync` stays on.
- README: the two systems in the systems table as experimental, the measured speed, the N64 controls, and how to save
  per-game options from the menu. Per-game options live on the root filesystem like every RetroArch setting, so a
  reflash resets them; the README says so (our call: moving RetroArch's config to `/roms` would change every system).

### Tests

- `tests/apps.sh`: both `.so` files exist, are ARMv7 (not v8, the same check as DOSBox Pure), and mupen64plus-next
  contains its ARM dynarec (a symbol or string only the dynarec build has).
- `tests/rootfs.sh`: the system count grows by two; the existing checks that every `es_systems` command goes through
  `ga36-retroarch` and names an installed core cover the new entries; the core option files ship with frame skip off
  for PPSSPP; the PPSSPP assets ship.
- `tests/roms-part.sh`: the folder list includes `n64` and `psp`.
- `tests/container.sh` (or wherever the container is checked): the cross toolchain and armhf headers are present.

### Checks on the device

As for the sticks and DOS: the owner flashes the card, copies the three games from their collection to `/roms`, and
plays; the builder reads the board over `scripts/board-run.sh` and tunes the option defaults in that loop. The
README and hardware notes get the numbers afterwards.


- `es2_info` (or equivalent) on the device: lima's GLES2 extensions, recorded.
- Super Smash Bros. and Mario Kart 64: start, play a match and a race, FN+Start back to ES. FPS from RetroArch's
  display (the N64 VI rate, so read it as a fraction of 60), and how it feels.
- Castlevania DXC: start, play the first stage. Does the music hold its speed and play cleanly? FPS and how it feels.
- Memory: RSS of RetroArch and free memory while each game runs, with ES in the background (512 MiB). If a game
  does not fit, the N64/PSP launch stops ES for the game's run and restarts it afterwards (decided with the owner).
- Governor `performance` while they run; a save survives a relaunch.
- A game that will not start returns to ES.

## Risks

- **Speed.** Expected (a guess): Smash playable but below full speed, Mario Kart choppy, Castlevania with music that
  slows in busy scenes. Recorded, not fixed.
- **lima.** GLideN64 crashes on lima when it uses dual-source blending (GLideN64 #2903); the libretro copy hard-codes it
  off. Mali-400 shaders are fp16 only, so textures may wobble. Unknown until tried.
- **Memory.** PPSSPP streams the ISO on 32-bit builds (no full-ISO cache); its footprint with ES running is unmeasured.
- **Cross build.** Both cores are normally built natively; the cross build may need fixes (the dynarec header
  generation, pkg-config paths, FFmpeg prebuilts). If one core resists, building it under qemu is the fallback, as long
  as CI still fits in 6 h.
